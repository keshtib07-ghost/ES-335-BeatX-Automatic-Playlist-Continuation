02 / Recommendation pipeline

How the recommender works

A seed is a song you choose as an example. Studio accepts up to 20 seeds. The walkthrough uses three. Each request uses the saved model; it does not retrain the model or analyse the seed audio.

What training produces

Song relationships

Song relationships

Collaborative filtering (CF) uses all 804,485 training playlists. Each song is counted once per playlist. Shared playlists indicate similarity. We adjust for popularity and give less weight to pairs seen together only a few times.

Title understanding

Title classifiers

TF-IDF converts title words and character patterns into numerical features. Both classifiers learn from all 804,485 training titles, using keyword-generated labels. Studio combines classifier predictions with explicit rules, including rules for negated phrases.

Song tags and popularity

Song context profiles

Apply the title classifier to every training playlist, then count the context evidence for its songs. Exact duplicate groups contribute once to this tag evidence. A smoothed association score, called lift, compares each song’s tag rate with the overall rate. Training frequency supplies the popularity fallback.

The full-title run kept the existing CF index. It retrained both title classifiers and rebuilt the song context profiles.

Case 1 / All three seeds appeared in training

Example: “Gym session” with three seed songs

A, B and C are example names. The following steps describe the implementation, not a measured recommendation result.

  1. Look up the seed IDs

    Look up each Spotify track ID and check whether it appeared in training. A matching song name is not enough. Seeds with training support can supply related songs.

  2. Read the requested context

    “Gym session” suggests workout context. The title classifier combines its prediction with keyword rules. Seed context uses tags supported by at least half of the seeds that have usable tags. When the title and seeds disagree within a category, the title takes priority. Your selected tags remain filter requirements.

  3. Build the song shortlist

    Each seed supplies up to 200 related songs. Similarity is cosine similarity multiplied by co-occurrence / (co-occurrence + 10), which reduces trust in rare pairs. Combine the lists and add each candidate’s score across seeds. Songs related to several seeds can receive more support. Exclude the seeds from the additions.

  4. Apply the selected filters

    A selected tag requires lift above 1. A BPM filter requires a known tempo within the selected range. An era filter requires accepted date metadata. If more songs are needed, add up to 5,000 popular training tracks to the shortlist. In this path, an inferred title tag can influence ranking without becoming a requirement for every result.

  5. Rank the eligible songs

    Scale the CF scores, then apply the configured context boost. The boost uses positive song-tag associations and is capped. Its weight defaults to 0 when no matching settings file is available. At weight 0, title context does not change the CF order, but selected filters and context-based fallback still work.

  6. Return the recommendations

    Return up to 20 eligible additions with notes about applied context and missing metadata. Verified recording IDs can remove duplicate releases when that mapping is available. Strict filters can leave fewer than 20 results. Playback flow reorders the chosen additions. Spotify export places your seeds first, followed by those additions.

The inputs have different roles. Seeds supply song relationships. The title suggests the intended context. Selected filters control eligibility.

Case 2 / Some or all seeds have no training evidence

When a seed was not seen during training

A Spotify track may be missing from the catalogue or present there without any training support. In either case, it supplies no learned song relationships. We do not substitute another track because its name looks similar.

  1. Use the seeds that have training support

    Known seeds still supply related songs and context. Unknown seeds are skipped for those calculations. The response reports how many of your seeds appeared in training.

  2. If no seed is usable, start with popular songs

    Without a usable seed, there is no CF score. A title such as “Gym session” can still supply context. The context-only path examines up to 50,000 popular training tracks using their saved tags. Selected-filter paths can also refill from popular tracks.

  3. Rank by context while enforcing your filters

    When no positive CF score is available, first prefer full context agreement. Then compare title matches and the number of matching context groups. Any era hint and context strength break further ties; popularity breaks the remaining ties. Selected filters still apply. Without selected tags, the output stays in the best available context group and may contain fewer than 20 songs.

  4. If no context is usable, use popularity

    A title such as “My playlist” may produce no tag. If neither seeds nor context provide useful evidence, return popular training songs that pass the active filters. Explain this fallback in the response. Missing metadata can still reduce the result count.

This path still recommends songs seen during training. It does not analyse an unfamiliar seed’s sound. A seed that appeared in training can also reach this fallback if it has no useful neighbours.

How to supply a song missing from the catalogue

Name search covers the model’s catalogue. You can also supply a valid Spotify track ID or link; the API can keep an unmatched ID as an unknown seed. That seed contributes no CF evidence. Alternate releases are merged only when a verified recording mapping is available.

What counts as a duplicate

[A, B, A] → {A, B}

Repeated copies of one Spotify track ID count once within a playlist. Different release IDs remain separate in this experiment, even when they refer to the same recording.

A reviewed mapping between release IDs could merge the same recording before a new split. Matching the title and artist alone is unreliable for live versions and remixes, or for re-recordings.

The three-seed benchmark hides every song except its three seeds. The seed-count study reserves 20 possible seeds and keeps the other songs hidden for every tested seed count. Their scores are not directly interchangeable.

Why we compare the same playlists

Every method receives the same seeds and hidden songs for each playlist. To estimate uncertainty, we resample whole groups of exact duplicate playlists 500 times. Grouping keeps dependent copies together.

The “title minus CF” interval estimates uncertainty in the difference between the methods. It does not describe uncertainty in either score on its own.

Does an unrecovered song mean a bad recommendation?

A recommendation outside the hidden-song set earns no credit. It may still suit the listener. MPD records playlist choices, but does not provide explicit dislikes or every song the listener might accept.

Recovering a hidden song and satisfying a listener are different outcomes.

05 / Models and design choices

Models and ranking scores

Compare a popularity baseline with CF. Then add title context to the same CF shortlist to test whether it improves the ranking.

M0 · Popularity

Popularity baseline

Recommend songs that appear in the most training playlists, excluding the seeds. This needs no knowledge of the request and also provides a fallback.

A recommender using the user’s seeds should improve on this simple baseline.

M1 · Item-based CF

Item-based collaborative filtering

Adjust shared-playlist counts for each song’s popularity using cosine similarity. Discount pairs seen together only a few times. Add scores across the seeds and combine their related-song lists.

This uses the playlist membership data directly. Sparse arrays avoid storing a full similarity matrix for every pair of tracks.

M2 / M3 · Contextual CF

CF with title context

Infer context tags from the title using keyword rules or a trained classifier. Boost shortlisted songs with positive association to those tags. If no context is inferred, keep the CF scores.

Using the same shortlist lets us measure the extra value of title context.

Teaching example · invented counts

Try the scoring formula

This worked example uses invented counts for one seed appearing in 100 playlists. Adjust the controls to see how the ranking changes.

similarity(s, t) = co(s, t) / √(freq(s) × freq(t)) × co(s, t) / (co(s, t) + α)
CF(t) = Σvisible seeds s similarity(s, t)
final(t) = CF(t) × [1 + w × meanrequested tags(max(log(lift), 0))]

The reported benchmark settings are α = 10 and w = 1. This example explains that scoring rule. Changing a slider recalculates only the example; it does not rerun an experiment. The scores are ranking weights, not probabilities.

Title model: features, labels and thresholds

Word features capture individual words and two-word phrases. Character patterns help with short titles and spelling variations. A separate logistic-regression classifier predicts each tag, so a title can receive several tags or none. Balanced class weights account for uneven label frequencies.

The validation labels come from keyword rules. Agreement with those labels shows how well the classifier reproduces the rules; it does not validate the song’s mood.

How song-tag associations and the shortlist are computed

Count one tag vote per exact training group. Smooth each song’s tag rate toward the overall training rate with strength 20, using playlists labelled in the relevant category as the denominator. Lift is the smoothed rate divided by that overall rate. Only positive log lift adds a boost. A missing weak label does not penalise the song.

Each seed supplies its 200 highest-scoring neighbours. The fixed settings are shrinkage 10 and smoothing strength 20; we have not published sensitivity tests for these choices. Disk-backed sparse arrays make the million-playlist run manageable. The shortlist still limits recovery: reranking cannot return a hidden song that never reaches it.

Unknown seeds add no co-occurrence evidence. In the benchmark, popularity fills the remaining slots when the shortlist contains fewer than 20 songs. Seeds are excluded from the additions.

Methods proposed but not evaluated

ALS and BPR were proposed, but this report contains no completed comparison with either. A fair comparison would use the same split and query inputs, with the same validation budget. It should report runtime and memory use alongside recovery and coverage. We cannot claim CF is better than an untested method.

Worked example: why the similarity score changes

Invented counts: A appears in 100 playlists, B in 100, and both appear together in 50. Their cosine similarity is 50 / √(100 × 100) = 0.5. With shrinkage 10, the final similarity is 0.5 × 50/60 ≈ 0.417.

If C appears in 10,000 playlists and co-occurs with A the same 50 times, its cosine is only 0.05. Co-occurrence with B is more distinctive. Separately, a pair seen together once gets a shrinkage multiplier of 1/11; one seen 100 times gets 100/110. Rare evidence receives less trust.

Across two seeds, candidate X with similarities 0.6 and 0 scores 0.6; candidate Y with 0.4 and 0.5 scores 0.9. Y receives support from both seeds. These numbers explain the mechanism and are not observed results.

What the title-model terms mean

TF-IDF gives title words and character patterns numerical weights. Distinctive terms receive more weight than common terms such as “playlist.” Logistic regression estimates whether each tag applies to the title.

Weak supervision means keyword rules provide approximate labels instead of having people review every title. The classifier can inherit errors in those rules. A Study label describes intended use; it does not prove the song improves concentration. TF-IDF is fitted on training titles only, so validation and test titles do not influence the vocabulary.

Live Studio / Unified recommendations

The unified Studio pipeline

The unified Studio code below was reviewed at commit 1fd19b1. Studio uses a 19-tag classifier trained on all 804,485 titles, along with the regenerated song-context associations. The standard 12-tag benchmark isolates a smaller retrieval and reranking pipeline.

Context sources

How the input signals are combined

Studio predicts 19 context tags across the categories shown in its filters. It combines learned predictions with keyword rules and handles explicit negation. A seed-derived tag needs support from at least half of the seeds that have usable tags, with lift above 1.

Within a category, title context takes priority when it conflicts with seed context. Selected tags are enforced separately as filters. The sources are therefore not treated as equal votes.

For example, study-related seeds can conflict with a Gym title. The title wins that inferred-context conflict. A manually selected filter still determines which songs are allowed.

Filters versus scores

Filtering and ranking are separate steps

A song must match a selected tag in every selected context category, with lift above 1. Tags within the same category act as alternatives. BPM filters exclude songs without a known tempo. Era filters use accepted dates, although a catalogue date may describe a later reissue.

When CF scores are available, the configured context boost can adjust them. With no seed evidence, rank popular training songs by context. With neither signal, use training popularity.

Filters decide which songs are allowed. Ranking decides their order. Returning fewer than 20 songs is valid when fewer pass the filters.

Studio’s context weight and fallback pools

Studio multiplies CF scores by a context adjustment. It does not automatically place every context match above every CF match. Refill paths can add up to 5,000 popular training tracks; the context-only path can examine up to 50,000. These are songs from training, not new evidence about an unfamiliar seed.

unified score(t) = normalized CF(t) × [1 + wunified × bounded context boost(t)]

The Studio weight defaults to 0 unless a matching ranking_settings.json is available. Its tuning script tests weights 0, 0.15, 0.35. This is separate from the 12-tag benchmark’s selected weight of 1. At weight 0, explicit filtering and context-only fallback still operate.

Implementation: ProfileRanker and expanded context taxonomy.

06 / Evaluation metrics

What the metrics measure

The main benchmark reports averages at K = 20. The explorer below changes K for a saved case. Recall counts recovered songs; NDCG also rewards earlier hits.

Measured case / K = 1 to 20

How scores change with K

Change K to score a longer prefix of the same saved ranking. This is one actual case from the earlier seed study, not a model average.

Why can the metrics move differently?

Increasing K cannot remove a recovered hit, so Recall and Hit Rate cannot fall for a fixed ranking. Precision can fall when the extra slots are misses. NDCG can move either way because its ideal ranking also changes with K. Moving K does not retrain the model.

    Studio / Failure analysis

    Studio failure cases

    These are measured live requests. They check behavior at difficult inputs. They do not measure recommendation accuracy or listening satisfaction.

    In the title-conflict check, changing “Study focus” to “Gym workout” kept all 20 songs but changed their order. A title can guide ranking without replacing the whole list. This is one case, not a general failure rate.

    Inspect each request

    Unknown seeds need a fallback.

    A song outside training has no learned neighbors. The system can use the known seeds or fall back to title context. This gives a usable response, but it does not learn the unknown song’s sound.

    Filters can leave no results.

    A narrow tempo range can leave no eligible songs. Unknown BPM is excluded rather than guessed. Returning an empty list is more accurate than claiming a match.

    A title is a clue.

    A gym title can conflict with calm seeds. The title changes context, while seed relevance still drives much of the order. A selected activity filter is the stronger eligibility requirement.

    Good recovery can still repeat artists.

    Co-occurrence can favor related songs from the same artist. The audit reports artist variety for each request. We have not tested a diversity reranker or measured whether listeners prefer one.

    10 / Findings and limitations

    Findings and limitations

    Context, not listener verification

    What a song tag actually means

    A Gym tag means the song appeared in training playlists with workout-related titles. It describes how playlist creators grouped the song. We did not ask listeners to verify its suitability for exercise. Misleading titles can produce wrong tags, while songs with little evidence may remain untagged.

    • Seed count. Recovery improves through 20 seeds. The validation rule selects 20, so the study gives no evidence that five or ten seeds are enough.
    • Title context. The three-seed benchmark shows a small average gain. It comes from playlists whose titles receive usable tags.
    • Title classifier. Keyword rules and the learned classifier give similar recommendation scores in the seed-count study. We have not established that the classifier improves on those rules.
    • Coverage. More seeds can improve recovery while reducing the number of distinct songs recommended across the sample. Neither result tells us whether listeners prefer the playlists.
    • Additional filters. The seed-tempo filter lowers recovery in the final Studio test. Bass features and release-date filtering still need separate comparisons.
    Limits of the evidence

    Limits of the evidence

    • Title labels. Titles provide approximate context. Human review is needed, especially for less common tags and unfamiliar language.
    • Incomplete preferences. MPD records songs people included. It cannot tell us every song they would accept or which ones they dislike.
    • Different release IDs. The same recording can have several Spotify IDs. Recommending an alternate release may receive no recovery credit.
    • Sample limits. The seed-count study uses playlists longer than 20 songs. Its results may not apply to shorter playlists or to every listener.
    • Earlier development data. The split keeps the 20,000-playlist pilot in training. We still need to check whether any other historical development samples overlap the test.
    • Reproduction. The charts use saved result files. Rebuilding this page does not independently verify the original training run.

    Next evaluations

    1. Check labels and the shortlist.Ask people to review a sample covering common and rare tags. Report accuracy for each tag and the fraction of hidden songs reaching the shortlist.
    2. Compare additional models.Evaluate ALS and BPR using the same split and seeds. Record runtime and memory use. Separately test whether reducing repeated artists improves variety without losing too much recovery.
    3. Test each added feature separately.Compare the models on the same playlists, adding one feature at a time. Report metadata coverage and incorrect matches. A context tag is not a measurement of bass.
    4. Ask listeners to judge the playlists.Decide the questions before collecting responses. Measure song fit and variety separately from hidden-song recovery. Use a fresh test sample after further tuning.

    Conclusion

    Answers to the research questions

    RQ1: recovery improved as seed count increased through 20. The validation rule selected 20, so the study does not establish an earlier stopping point. RQ2: title context added a small positive gain to CF in the three-seed benchmark. CF itself produced the largest improvement over popularity. Better recovery can coincide with lower catalogue coverage.

    The final Studio evaluation gives NDCG@20 of 0.26347, compared with 0.26245 for CF. The confidence interval for their difference includes zero. The tested tempo filter lowers recovery. Listening satisfaction still needs a listener study.

    Reproduce the full experiment locally

    Use Python 3.12, Git and a separate working directory. Obtain your own authorized Spotify MPD archive and replace the archive path below. The pinned Python dependencies are in requirements.txt. Keep the original completed run; these steps create a local reproduction and do not deploy it.

    1. Set up the source and environment

    git clone https://github.com/keshtib07-ghost/ES-335-BeatX-Automatic-Playlist-Continuation.git beatx-reproduction
cd beatx-reproduction
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export PYTHONPATH="$PWD/src"
export OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1
export MPD_ZIP="/path/to/your/authorized-mpd.zip"
git rev-parse HEAD
python --version
python -m pip freeze

    Record the commit and environment with the run. The shell commands use Bash, for example Linux or WSL. The source manifest pins the 20,000-playlist development pilot; it is not a checksum manifest for the entire million-playlist archive.

    2. Prepare, split and verify the data

    python scripts/prepare_million.py scan --zip "$MPD_ZIP"
python scripts/prepare_million.py prepare --zip "$MPD_ZIP" --output runs/million
python scripts/prepare_million.py verify --output runs/million
python scripts/split_million.py build
python scripts/split_million.py verify

    Preparation writes runs/million/mpd.sqlite3 and prep_summary.json. Splitting writes split.sqlite3 and split_summary.json. The grouped split targets 80/10/10; the documented pilot and its exact copies stay in training. Verifiers reconcile counts and check database integrity. See the preparation guide for the input format and verified-alias option.

    3. Fit and evaluate the standard 12-tag benchmark

    python scripts/train_million.py --run runs/million/model-full-titles index
python scripts/train_million.py --run runs/million/model-full-titles tags --title-training-limit 804485
python scripts/train_million.py --run runs/million/model-full-titles validate --queries 5000
python scripts/train_million.py --run runs/million/model-full-titles test

    The fit uses training playlists and titles. Validation selects the context weight and writes frozen_settings.json; test reads that choice and writes test_metrics.json. These commands target the documented split with 804,485 training playlists. The run directory also contains the index, tagger, training summaries and validation metrics. Existing completed stages are reused only when their identities match; test refuses to overwrite its existing output.

    4. Rebuild the public benchmark and downloads

    python scripts/export_site_results.py --input runs/million/model-full-titles/test_metrics.json --output docs/experiment.js
python scripts/export_research_bundle.py
python scripts/export_research_bundle.py --check
python -m http.server 8765 --directory docs

    Open http://localhost:8765/research.html for the Summary and research-deep-dive.html for the full report. Compare the exported benchmark with its saved metrics; --check verifies download fidelity, not model quality. This static server runs the Research interactions. Studio inference uses its configured Python API.

    Which provenance records are needed for an exact rerun?
    Public evidence and original-run records are different.
    RecordWhat is available / still needed
    Source archiveThe pilot manifest is public. The original full archive’s complete identity and checksum record are not included in the public bundle; preserve them with the scan and preparation summary.
    Preparation and splitThe code and reported counts are public. Keep the original prep_summary.json, split_summary.json, verifier outputs, split identity and any recording-map checksum. Those full-run records are not published here.
    Model and query identityThe benchmark export includes the frozen-settings hash and sampled-query fingerprint. An exact rerun also needs the original frozen settings, matching index/tag summaries and checkpoints. Public aggregate hashes do not validate every private model array.
    Code and environmentRecord the Git commit, Python version, dependency versions and commands. Requirements are pinned, but the complete original machine/run manifest is not part of the public evidence bundle.

    Keep raw data and trained per-track files local unless sharing is permitted. Recreating the public charts from saved aggregates is lighter than independently reproducing the full training run. Missing original records must be supplied by the run owner; they are not reconstructed or invented by this page.
