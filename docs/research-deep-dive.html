First / How our model works

From your request to a playlist

A seed is an example song you supply. The walkthrough describes the current unified Studio code, using three seeds for clarity; Studio supports up to 20. Generation uses saved training evidence. It does not retrain for each request or listen to the seed audio.

Before you enter anything: what did training prepare?

Song relationships

Learn what appears together.

All 804,485 training playlists supply binary song memberships. Collaborative filtering (CF) measures how often songs appear together, normalizes for their popularity, and discounts pairs with little evidence.

Title understanding

Learn context from names.

Word and character TF-IDF turn titles into numerical features. Both classifiers learn from all 804,485 training titles using labels supplied by keyword rules. Studio’s expanded profiles combine classifier predictions with rules and respect explicit negation.

Song tags and popularity

Connect context to songs.

Score titles across all training playlists and aggregate evidence for their songs, combining exact duplicate groups. Smoothed lift measures association above a context’s background rate. Training frequency also provides the popularity fallback.

The full-title run reused the established CF index and rebuilt the classifiers and song-context evidence.

Case 1 / All three seeds appeared in training

Example request: “Gym session” + songs A, B and C

A, B and C are illustrative names. Here is what happens after you press Generate.

  1. Recognize the songs.

    The API resolves the supplied Spotify track IDs to catalogue entries and checks their training counts. A known name alone is not enough: the model uses track identity. The three recognized seeds can contribute learned neighbour evidence.

  2. Read the playlist title and seed context.

    “Gym session” supplies a workout cue. The expanded title pipeline combines keyword rules and logistic-regression predictions. Separately, it finds context associations supported by at least half of the seeds that have usable tags. Title context takes priority over conflicting seed context within a category; selected tags are handled as filters.

  3. Retrieve candidates with CF.

    For each seed, find up to 200 neighbours using cosine similarity multiplied by the shrinkage factor co-occurrence / (co-occurrence + 10). Merge the neighbour lists and add scores across the seeds. A song supported by A, B and C can receive more evidence than one supported by just A. Remove the seed tracks themselves.

  4. Apply requirements and refill when needed.

    Selected tags require above-background association. Selected BPM ranges require known tempo within the range; era filters need accepted date evidence. If the pool needs more options, the ranker can add popular training songs, using a refill pool of up to 5,000 on these paths. A title by itself is a ranking clue, not a hard requirement that every result carry that tag.

  5. Rank with seed relevance and optional context.

    Normalize the CF scores, then apply a bounded multiplicative context boost when the configured weight is positive. Positive song–tag lift supplies the context evidence. The unified weight defaults to 0 without a matching settings file, so a title does not necessarily change seed-based ordering. Explicit filters and context-based fallback still work at weight 0.

  6. Return up to 20 additions.

    Return the best eligible songs, along with applied context and any fallback or metadata notes. Reviewed recording IDs can suppress verified alternate-release duplicates when that metadata is available. Tight filters may produce fewer than 20 songs. Optional playback ordering rearranges the selected songs; Spotify export saves them, rather than generating the ranking.

In plain language: the seeds say “find songs connected to these”; the title says “this is the intended context”; selected filters say “these requirements must be satisfied.” CF and tagging contribute different kinds of evidence.

Case 2 / Some or all seeds have no training evidence

What if the seed song does not match the training catalogue?

A valid Spotify ID can be outside the local catalogue, or present in the staged data without ever appearing in training. Neither provides learned co-occurrence evidence. The system does not guess a match merely because another song has a similar name.

  1. If one or two seeds are known, use them.

    Unknown seeds add no CF evidence. The recognized seeds still retrieve neighbours and contribute context, so the system does not throw away the whole seed set. The response reports how many supplied seeds were seen in training.

  2. If none is usable, start from training popularity.

    There is no seed-based similarity score to trust. With a title such as “Gym session,” the model still infers workout context. It can examine up to 50,000 popular training tracks on the inferred-context-only path and use their saved song-tag associations. Selected-filter paths can also use a popular-track refill pool.

  3. Use the strongest available context and the selected filters.

    Without positive CF scores, the ordering prioritizes full inferred-context agreement, title-context matches, the number of matched context groups, any title-era hint and context strength. Training-popularity order breaks remaining ties. Selected tags, BPM and era requirements still constrain eligibility. Without explicit selected tags, the output stays within the best available context tier and may be short.

  4. If context is missing too, fall back to popularity.

    A vague title such as “My playlist” may yield no usable tag. With no usable seed or context evidence, return popular training songs subject to any active filters. The response explains the fallback. Limited context or metadata can leave fewer than 20 eligible results.

This is a fallback, not learning an unseen song. The model still recommends training-known tracks. It has not listened to the unfamiliar seed or discovered its musical properties. A training-known seed with no useful neighbours can also end up on a context/popularity path.

How does an unfamiliar song enter Studio?

Name search looks in the local catalogue; it does not search all of Spotify. A valid Spotify track ID or track link outside that catalogue can be represented as an unknown seed by the API. Missing training support and unfamiliar catalogue identity both prevent CF evidence. Alternate releases count as the same recording only when a verified mapping is available.

Fact-checked against request handling, unified ranking and expanded title tagging. Implementation settings and deployment details follow in the report.

Why paired comparisons?

Each method receives the same seeds and references for a query. Confidence intervals resample exact playlist groups, preserving dependence among duplicate copies. The reports use 500 bootstrap resamples.

An interval for “title minus CF” describes the paired difference. It is not an interval for either individual model score.

What is not a negative example?

An unheld-out recommendation earns no recovery credit. It may still be a good song for the listener. MPD contains observed playlist choices, not explicit dislikes or a complete list of all relevant music.

Why: offline relevance and subjective fit answer different questions.

04 / Methods & design decisions

Why we chose these methods

Start with a cheap baseline, learn associations from shared playlists, then ask whether title context adds information.

M0 · Popularity

What is common?

Rank by training-playlist frequency, excluding visible seeds. It needs no query understanding and is also a fallback when there is no seed evidence.

Why keep it: a personalized model should beat a useful, reproducible nonpersonalized baseline.

M1 · Item-based CF

What co-occurs?

Cosine normalizes pair counts by each track’s frequency. Shrinkage reduces trust in rare pairs. Sum evidence over seeds and keep a sparse candidate union.

Why this method: it directly uses MPD’s strongest signal and avoids a dense track-by-track matrix.

M2 / M3 · Contextual CF

What fits the request?

Infer title tags with rules or a learned text model. Boost candidates with positive, smoothed association to those tags. Unknown context leaves CF unchanged.

Why rerank: preserve seed relevance while isolating the contribution of context.

Teaching example · invented counts

Open up the ranking score.

One seed with frequency 100. These three tracks are illustrative, not MPD observations.

similarity(s, t) = co(s, t) / √(freq(s) × freq(t)) × co(s, t) / (co(s, t) + α)
CF(t) = Σvisible seeds s similarity(s, t)
final(t) = CF(t) × [1 + w × meanrequested tags(max(log(lift), 0))]

For Experiments A/B, α = 10 and w = 1. This teaching tool illustrates their benchmark scoring, not the newer unified ranker. Moving a slider does not retrain or reevaluate a model. Scores are ranking weights, not probabilities.

Why TF-IDF + logistic regression for titles?

Word unigrams/bigrams capture phrases; character n-grams help with spelling and short text. Independent binary classifiers allow several tags or none. Balanced class weights address unequal weak-label frequencies. This is a modest text baseline that can be inspected and run locally.

The measured taxonomy is sad, chill, upbeat, gym, study, sleep, dance, party, rave, rainy, summer and winter. For each tag, validation tests cutoffs {0.50, 0.60, 0.70, 0.80, 0.90, 0.95}; it chooses the best F1 among cutoffs with at least 3 predicted positives and 0.65 precision, breaking ties toward the higher cutoff. If none qualifies, the cutoff is 0.90. These are design choices, not demonstrated universal optima.

Agreement with keyword-derived validation labels measures reproduction of weak supervision. It does not establish emotion recognition or reliable audio mood.

Why smoothing, positive lift and sparse neighbours?

Tag evidence counts one vote per exact training group. A tag rate is smoothed toward its training prior with strength 20, using the relevant labeled category as denominator. Lift compares that rate with its prior. Only positive log lift boosts a track; weakly labeled absence is not treated as evidence of incompatibility.

Each seed contributes its top 200 shrinkage-adjusted neighbours. Shrinkage 10, neighbourhood size 200 and smoothing strength 20 are fixed reference settings; the public results do not contain sensitivity studies proving them optimal. Training indices are stored as disk-backed sparse arrays. This makes the million-playlist run practical, but caps retrieval: reranking cannot recover a reference that never enters the candidate pool.

Unknown seeds contribute no co-occurrence evidence. If fewer than 20 candidates exist, popularity fills the remaining slots. Visible seeds are excluded.

Why not ALS, BPR or a deep model already?

ALS and BPR were proposal candidates, not completed comparisons in this full-run report. More parameters do not establish a better system. Add them as controlled baselines using the same split, seeds, references and validation budget; report compute and coverage alongside quality. No claim that CF outperforms those untested methods is supported here.

A worked example: cosine, shrinkage and several seeds

Invented counts: A appears in 100 playlists, B in 100, and both appear together in 50. Their cosine similarity is 50 / √(100 × 100) = 0.5. With shrinkage 10, the final similarity is 0.5 × 50/60 ≈ 0.417.

If C appears in 10,000 playlists and co-occurs with A the same 50 times, its cosine is only 0.05. Co-occurrence with B is more distinctive. Separately, a pair seen together once gets a shrinkage multiplier of 1/11; one seen 100 times gets 100/110. Rare evidence receives less trust.

Across two seeds, candidate X with similarities 0.6 and 0 scores 0.6; candidate Y with 0.4 and 0.5 scores 0.9. Y receives support from both seeds. These numbers explain the mechanism and are not observed results.

What do TF-IDF, logistic regression and weak supervision mean?

TF-IDF turns title words and character patterns into numerical features. Distinctive terms can carry more information than common words such as “playlist.” Logistic regression is used here for classification: each tag has a model estimating whether it applies to the title.

Weak supervision means approximate keyword rules supply training labels rather than independently reviewed human judgments for every title. This makes labels inexpensive, but the learned classifier can inherit the rules’ mistakes. “Study” is an intended use, not proof that a song improves concentration. Training-only TF-IDF fitting keeps held-out text out of vocabulary learning.

Live Studio / Unified recommendations

How Studio ranks songs

The unified Studio code below was reviewed at commit 1fd19b1. Studio uses a 19-tag classifier trained on all 804,485 titles, along with the regenerated song-context associations. The standard 12-tag benchmark isolates a smaller retrieval and reranking pipeline.

Context sources

Different inputs have different jobs.

Expanded title context combines rules and learned tags, respects explicit negation, and uses 19 tags across mood, theme, weather, party and activity. Seed context uses above-background associations supported by at least half of the seeds with usable tags.

Title context takes priority over conflicting seed context within a category. Selected tags are handled separately as eligibility requirements. The system does not average these three sources as equal votes.

Example: a study-like seed set and a gym title can disagree. Inferred title context wins that conflict; an explicit selected tag still constrains which songs are eligible.

Filters versus scores

Allowed first. Ordered second.

A selected context category requires positive association (lift above 1). Alternatives within that category can match; selections across categories must each match. Selected BPM ranges exclude unknown tempo. Era filters use accepted date evidence; a catalogue edition can be a later reissue.

When seed scores exist, a bounded context boost adjusts normalized CF scores. Without seed evidence, context ranks a training-popularity pool. Without either signal, training popularity is the fallback.

A filter answers “is it eligible?” A score answers “where does it rank?” Fewer than 20 matching songs is an allowed outcome.

What changed in the ranking?

The latest code preserves seed evidence through a multiplicative adjustment rather than always sorting context matches ahead of CF. It can expand the candidate pool with up to 5,000 popular training tracks on refill paths, or up to 50,000 for context-only retrieval without usable seeds. This helps fill filters; it does not create evidence for training-unseen songs.

unified score(t) = normalized CF(t) × [1 + wunified × bounded context boost(t)]

The unified boost defaults to 0 unless a matching local ranking_settings.json is present. Its tuning grid is {0, 0.15, 0.35}; this is separate from the benchmark’s selected weight 1. Zero boost still allows explicit filtering and context-only fallback. The standard benchmark’s selected weight and scores describe the 12-tag reranker.

Implementation: ProfileRanker and expanded context taxonomy.

How is the unified ranker evaluated?

evaluate_unified.py defines up to 300 fresh held-out playlists with exactly 20 tracks: five visible seeds and 15 hidden references. It compares seeds-only, seeds-plus-title, and unified output. tune_unified.py compares boost weights on up to 150 validation queries and scores the selection on up to 150 fresh test queries, excluding earlier cohorts.

The expanded-profile build also checked 5,000 validation titles. It flagged 55 ambiguous titles and 2 rule/classifier disagreements. That checks title labels, not recommendation quality. The final Studio test below uses a separate frozen protocol.

05 / Metrics, with the arithmetic

Understanding the metrics

The main benchmark reports averages at K = 20. The explorer below changes K for a saved case. Recall counts recovered songs; NDCG also rewards earlier hits.

Measured case / K = 1 to 20

How much should we recommend?

Change K to score a longer prefix of the same saved ranking. This is one actual case from the earlier seed study, not a model average.

Why can the metrics move differently?

Increasing K cannot remove a recovered hit, so Recall and Hit Rate cannot fall for a fixed ranking. Precision can fall when the extra slots are misses. NDCG can move either way because its ideal ranking also changes with K. Moving K does not retrain the model.

    Studio / Failure analysis

    Where can a request go wrong?

    These are measured live requests. They check behavior at difficult inputs. They do not measure recommendation accuracy or listening satisfaction.

    In the title-conflict check, changing “Study focus” to “Gym workout” kept all 20 songs but changed their order. A title can guide ranking without replacing the whole list. This is one case, not a general failure rate.

    Inspect each request

    Unknown seeds need a fallback.

    A song outside training has no learned neighbors. The system can use the known seeds or fall back to title context. This gives a usable response, but it does not learn the unknown song’s sound.

    Filters can leave no results.

    A narrow tempo range can leave no eligible songs. Unknown BPM is excluded rather than guessed. Returning an empty list is more accurate than claiming a match.

    A title is a clue.

    A gym title can conflict with calm seeds. The title changes context, while seed relevance still drives much of the order. A selected activity filter is the stronger eligibility requirement.

    Good recovery can still repeat artists.

    Co-occurrence can favor related songs from the same artist. The audit reports artist variety for each request. We have not tested a diversity reranker or measured whether listeners prefer one.

    09 / Interpretation & limitations

    What the results mean

    Context, not listener verification

    What the tags mean

    We infer tags from playlist titles in the training data. A Gym tag means the song appeared in playlists whose titles suggested a workout. It describes how people grouped the song. We didn’t ask listeners to verify that it works for a workout. Playlist titles can be vague or misleading, and songs with little evidence may have no tag. Treat these tags as useful clues about context.

    Limits of the evidence

    Where the conclusion could change.

    • Weak labels: titles are noisy proxies for context. Language, slang and minority tags need human-reviewed evaluation.
    • Exposure bias: MPD captures existing playlist choices, not all acceptable recommendations or explicit dislikes.
    • Identity: exact Spotify IDs can split one recording across releases and penalize acceptable aliases.
    • Sampling: the seed study uses longer playlists and a fixed sample, not every listener or every test playlist.
    • Provenance: the documented split protects the 20k pilot. Exclusion of any other historical development cohorts requires a separate audit.
    • Reproduction: this page derives views from published aggregates; private databases and model arrays were not rerun or independently verified for this report.

    The next experiments, in a useful order

    1. Audit labels and retrieval.Human-review stratified title samples; report per-tag coverage/F1 and candidate recall before reranking.
    2. Add controlled model baselines.Compare ALS/BPR, compute and memory using the same untouched protocol; test a simple diversity reranker.
    3. Evaluate enrichment as an ablation.Document match quality and field coverage. Compare CF, +context, +BPM and combinations on the same eligible cohort; report missingness separately. Bass requires measured features, not a gym/romance label.
    4. Run a fresh listener study.Freeze hypotheses, measure perceived fit and diversity, and keep it distinct from offline recovery. Future tuning needs a fresh holdout.

    Conclusion / Answers to the research questions

    Answers to our questions

    Collaborative filtering is the strongest established improvement over popularity. In Experiment A, title context adds a small positive overall gain. Experiment B shows better recovery with more seeds through 20, without establishing an early plateau. Coverage can decline as recovery improves.

    We have not established that the newer unified ranker, BPM or bass improves recommendation quality, or that offline recovery predicts listening satisfaction. These need their own controlled evaluations. The current evidence supports a useful co-occurrence recommender with limited title-context gains.

    Reproduce the full experiment locally

    Use Python 3.12, Git and a separate working directory. Obtain your own authorized Spotify MPD archive and replace the archive path below. The pinned Python dependencies are in requirements.txt. Keep the original completed run; these steps create a local reproduction and do not deploy it.

    1. Set up the source and environment

    git clone https://github.com/keshtib07-ghost/ES-335-BeatX-Automatic-Playlist-Continuation.git beatx-reproduction
cd beatx-reproduction
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export PYTHONPATH="$PWD/src"
export OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1
export MPD_ZIP="/path/to/your/authorized-mpd.zip"
git rev-parse HEAD
python --version
python -m pip freeze

    Record the commit and environment with the run. The shell commands use Bash, for example Linux or WSL. The source manifest pins the 20,000-playlist development pilot; it is not a checksum manifest for the entire million-playlist archive.

    2. Prepare, split and verify the data

    python scripts/prepare_million.py scan --zip "$MPD_ZIP"
python scripts/prepare_million.py prepare --zip "$MPD_ZIP" --output runs/million
python scripts/prepare_million.py verify --output runs/million
python scripts/split_million.py build
python scripts/split_million.py verify

    Preparation writes runs/million/mpd.sqlite3 and prep_summary.json. Splitting writes split.sqlite3 and split_summary.json. The grouped split targets 80/10/10; the documented pilot and its exact copies stay in training. Verifiers reconcile counts and check database integrity. See the preparation guide for the input format and verified-alias option.

    3. Fit and evaluate the standard 12-tag benchmark

    python scripts/train_million.py --run runs/million/model-full-titles index
python scripts/train_million.py --run runs/million/model-full-titles tags --title-training-limit 804485
python scripts/train_million.py --run runs/million/model-full-titles validate --queries 5000
python scripts/train_million.py --run runs/million/model-full-titles test

    The fit uses training playlists and titles. Validation selects the context weight and writes frozen_settings.json; test reads that choice and writes test_metrics.json. These commands target the documented split with 804,485 training playlists. The run directory also contains the index, tagger, training summaries and validation metrics. Existing completed stages are reused only when their identities match; test refuses to overwrite its existing output.

    4. Rebuild the public benchmark and downloads

    python scripts/export_site_results.py --input runs/million/model-full-titles/test_metrics.json --output docs/experiment.js
python scripts/export_research_bundle.py
python scripts/export_research_bundle.py --check
python -m http.server 8765 --directory docs

    Open http://localhost:8765/research.html for the Summary and research-deep-dive.html for the full report. Compare the exported benchmark with its saved metrics; --check verifies download fidelity, not model quality. This static server runs the Research interactions. Studio inference uses its configured Python API.

    Which provenance records are needed for an exact rerun?
    Public evidence and original-run records are different.
    RecordWhat is available / still needed
    Source archiveThe pilot manifest is public. The original full archive’s complete identity and checksum record are not included in the public bundle; preserve them with the scan and preparation summary.
    Preparation and splitThe code and reported counts are public. Keep the original prep_summary.json, split_summary.json, verifier outputs, split identity and any recording-map checksum. Those full-run records are not published here.
    Model and query identityThe benchmark export includes the frozen-settings hash and sampled-query fingerprint. An exact rerun also needs the original frozen settings, matching index/tag summaries and checkpoints. Public aggregate hashes do not validate every private model array.
    Code and environmentRecord the Git commit, Python version, dependency versions and commands. Requirements are pinned, but the complete original machine/run manifest is not part of the public evidence bundle.

    Keep raw data and trained per-track files local unless sharing is permitted. Recreating the public charts from saved aggregates is lighter than independently reproducing the full training run. Missing original records must be supplied by the run owner; they are not reconstructed or invented by this page.
